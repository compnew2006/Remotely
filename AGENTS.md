# AGENTS.md

Remotely — a remote control and remote scripting solution built with .NET 10 (LTS retarget ratified — AD-16), Blazor, and SignalR Core. Upstream: https://github.com/immense/Remotely

## Setup commands

- Restore deps: `dotnet restore Remotely.sln`
- Build:        `dotnet build Remotely.sln` — **fails here (`NETSDK1045`)**; use `& "$env:USERPROFILE\.dotnet\dotnet.exe" build Remotely.sln` (SDK 10.0.403) until the machine-level install lands. Last recorded result: **0 errors, 44 warnings** (T-11).
- Test:         `& "$env:USERPROFILE\.dotnet\dotnet.exe" test Remotely.sln`   # MSTest; CI runs `dotnet test` at repo root on push/PR to `master`. **Locally executable only via the explicit user-profile SDK path** — see Testing instructions.
- Run server:   `dotnet run --project Server/Server.csproj`   # ASP.NET Core + Blazor + SignalR
- Run desktop:  `dotnet run --project Desktop.Linux/Desktop.Linux.csproj` (Linux) or `Desktop.Win/Desktop.Win.csproj` (Windows)
- Publish:      `Utilities/Publish.ps1`  ·  migrations: `Utilities/Add-Migration.ps1` / `Update-Database.ps1`
- Docker:       `docker-compose/docker-compose.yml`  # single service `immybot/remotely:latest`, port 5000 (HTTP), volume `/var/www/remotely` → `/app/AppData`. **No Caddyfile exists in the repo** — Caddy is the only supported reverse proxy (per README) but must be supplied separately.
- There is no npm build step: the browser client in `Server/wwwroot/src` is TypeScript compiled by `Microsoft.TypeScript.MSBuild` during `dotnet build`. Third-party browser libs now come from **npm** (`Server/package.json` + `package-lock.json`; `npm install && npm run sync-libs` refreshes `wwwroot/lib`), replacing the removed LibMan restore. **The compiled `.js`/`.js.map` and `wwwroot/lib/*` are committed** — regenerate and commit them with any `.ts`/dependency change, or the shipped client stays stale. `@msgpack/msgpack@3.0.0-beta2` is deprecated (E-45): upgrade it together with `@microsoft/signalr-protocol-msgpack` (protocol versions are coupled).

## Feature additions in this fork (2026-11-06)

Owner-directed extensions to the upstream Remotely fork. They are listed here because they change how the server and the desktop client are deployed and operated — not because they are upstream features.

- **Task Manager** — device card **Actions → Task Manager** (`Server/Components/ModalContents/TaskManagerModal.razor`): lists the processes running on a device (name, PID, session, memory, CPU, start time) and can end them. Built on the existing script channel, so **it works with agents that are already deployed** — no agent update needed.
- **Screenshots / monitoring** — device card **Actions → Screenshots** (`Server/Components/ModalContents/ScreenshotModal.razor`): the device captures full screenshots of its desktop at a fixed interval (1–30 minutes) **with no viewer attached**, and the server stores them. Per-device settings live on `Device`: `ScreenshotDirectory` (folder on the server), `ScreenshotRetentionCount`, `ScreenshotRetentionHours`, and `ScreenshotPauseWindows` (JSON list of start/end hours — **several exception windows per device are allowed**, and a window may wrap past midnight). A **"Take screenshot now"** button captures on demand with no schedule at all. Individual screenshots can be deleted, and the whole set cleared.
- **Camera clips / scheduled recording (SPEC-003, AD-20)** — device card **Actions → Camera** (`Server/Components/ModalContents/CameraModal.razor`): x64/x86 Windows desktop clients record MP4 clips; manual and scheduled captures are serialized. **The video source is a camera *or* a display** (`ScreenRecorderLib.DisplayRecordingSource`), and **the audio is off, the system audio, or a microphone** (`LoopbackAudioSource` / `CaptureAudioSource`) — both picked in the modal (AD-20). Schedules run every 1–30 minutes, honor multiple pause windows (including overnight windows), resume after the desktop client reconnects, and are not restored after a server restart. Stopping the current clip is separate from stopping the schedule. Camera settings are independent per device: default folder `AppData/Camera/<DeviceId>`, 200 clips, and 24 hours; each device can override its folder/count/retention/pause windows without changing screenshot settings. `ScreenRecorderLib` is unavailable in AnyCPU and Linux builds; devices need a compatible updated desktop client for recording. This host has no camera and no sound device, so live capture remains unverified.
- **Audio capture / live listening (SPEC-004, AD-19)** — device card **Actions → Audio** (`Server/Components/ModalContents/AudioModal.razor`): Windows desktop clients record WAV clips from **system audio** (loopback) or the **microphone**, with manual and scheduled captures that are serialized. Schedules run every 1–30 minutes, honor multiple pause windows, resume after the desktop client reconnects, and are not restored after a server restart. Audio settings are independent per device: default folder `AppData/Audio/<DeviceId>`, 200 clips, and 24 hours. **Live listening** works from the device card (independent of a control session) and through the existing in-session audio button; the live path never stores anything on the server. The capture engine is **NAudio 2.2.1**, which `Desktop.Win` already referenced — no new dependency — so the feature is Windows-only. **Recorded without the employee's consent or any notification** (owner decision AD-19, a recorded deviation from constitution Principle III — G6 stays UNKNOWN, G7 stays FAIL). The in-session viewer audio path is unchanged.
- **A session switch no longer kills the stream** (E-51) — `Desktop.Shared/Services/ScreenCaster.cs` now stops the capture **only** on `SessionLogoff`. Locking the screen, unlocking it, or an RDP connect/disconnect used to end the remote-control session with "Stream ended".
- **Deploying the desktop client is version-locked** (E-57) — `Utilities/Publish.ps1` stamps `AssemblyVersion` with the build timestamp (`yyyy.MM.dd.HHmm`, e.g. `2026.11.6.1438`). Replacing a DLL that was built **without the same `/p:Version`** fails at runtime with `Could not load file or assembly 'Shared, Version=…'`. Always publish with the same version, or publish the whole package through `Utilities/Publish.ps1`.
- **Screenshots need the new desktop client** — monitoring and the on-demand capture live in the desktop client (`Desktop.Shared/Services/ScreenMonitor.cs`); a device running an older build answers the server's `StartMonitoring` with nothing. Update the desktop client on each device (the agent itself needs no change).
- **Capture limits** — the client compresses every screenshot to ≤ 80 KB (`MaximumReceiveMessageSize` is 100 KB) and uses the DirectX path before BitBlt, because BitBlt of the secure desktop returns a black image while the session is locked.
- **The viewer's connection survives a backgrounded tab** — `ClientTimeoutInterval` is 2 minutes, the browser client reconnects on its own (`withAutomaticReconnect`) and re-requests the stream, and an unattended session survives 10 minutes without a viewer.

## Security

- Never commit secrets; `Server.csproj` uses `UserSecretsId`, so local credentials stay in user secrets — not in committed settings.
- `Server/Options/ApplicationOptions.cs` holds DB provider, HTTPS enforcement, and known-proxy lists — do not commit credentials or widen `KnownProxies` casually.
- The server is internet-facing behind a reverse proxy: forwarded headers (`X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-For`) are trusted only for configured proxies.
- **View Only is not an authorization boundary.** `RemoteControlSession.ViewOnly` is written once (`CircuitConnection.cs:266`), never read on the relay path, never sent to the agent, and reset to `false` on session clone. The controls that *are* enforced are: device-group membership (`DataService.DoesUserHaveAccessToDevice`), the session `accessKey` match (`ViewerHub.cs:210-221`), `EnforceAttendedAccess` consent, and the OTP viewer filter. Build any new authorization on those, never on View Only. **(Staleness caveat, updated at Phase-4 closing):** this paragraph was verified against the pre-`94d118c5` tree. `94d118c5` (landed by the parallel owner-directed session) added `SessionInfo.ViewOnly` checks that are now visible at `Server/Hubs/ViewerHub.cs:90,203,243,260-262` and a `viewOnly` parameter through `CircuitConnection.cs:34,218`, so **“never read on the relay path” is no longer literally true** — but that code has **not been security-audited here** (OD-11), G1 remains **FAIL** without a `[RELEASE-GATE]`, and the device-side enforcement claim still needs re-verification. Re-read `ViewerHub.cs`/`CircuitConnection.cs`/`Desktop.Shared/Services/Viewer.cs` before building on either version of this paragraph.
- **The interactive desktop process runs as SYSTEM, not as the logged-on employee.** `Desktop.Native/Windows/Win32Interop.cs:121-145` duplicates **winlogon's** token (`DuplicateTokenEx` → `TokenPrimary`) and `winlogon.exe` runs as `NT AUTHORITY\SYSTEM`; `Win32Interop.cs:158` places it on `winsta0\<desktop>` of the target session. `Agent/Services/Windows/AppLauncherWin.cs:41,111` falls back to `Process.Start` only when the agent itself is not SYSTEM. ⇒ "interactive session" ≠ "employee identity". `ResolveDesktopName` returns `"Winlogon"` (secure desktop) during logon/UAC.
- **The agent and the desktop client are visible in Task Manager, and that cannot be changed on Windows 11.** Hiding a running process from Task Manager is not supported: Task Manager enumerates every process, and `ProcessHideFromDebugger` / `SW_HIDE` / `WS_EX_TOOLWINDOW` do not remove a process from its list — real invisibility requires *not having a process of your own* (hosting the service inside `svchost.exe` as a `ServiceDll`, i.e. native code, or DLL injection into a live process). What Remotely does instead (E-50, 2026-11-06): `Agent/Services/Windows/DesktopProcessSupervisor.cs` watches the desktop client in the target session and restarts it with the same arguments when it exits uncleanly (exit code `0` = intentional shutdown, never restarted), with exponential backoff and a 5-attempts-per-minute cap; `Server/wwwroot/Content/Install-Remotely.ps1` sets an explicit service DACL (stop/reconfigure = administrators + SYSTEM only) plus `failureflag 1` and `restart/1000/5000/restart/15000`. ⇒ Killing `Remotely_Desktop.exe` from Task Manager now costs the user nothing; killing `Remotely_Agent.exe` gets the service restarted by SCM. The desktop client is launched as **SYSTEM** via a duplicated winlogon token, so a non-admin user cannot terminate it at all. **True hiding (svchost-hosted service) is tracked as OD-15 and was deliberately not implemented** — do not start it without an owner directive and a spec.

The superseded v1.0.0 is preserved verbatim at `.specify/memory/constitution.v1.0.0.superseded.md`; the exact diff is `CONSTITUTION-v2.0.0.diff`. **Never edit the constitution to make your own change fit — propose an amendment and let the owner ratify it; the constitution forbids the implementing agent from self-approving one.**
